WatchDog User Guide

WatchDog is a desktop application for managing dog daycare customers and dogs, optimized for use through a Command Line Interface (CLI) while retaining the benefits of a Graphical User Interface (GUI). If you type quickly, WatchDog can help you manage daycare records faster than traditional GUI applications.

Quick start

  1. Ensure that Java 25 or later is installed on your computer.
    Mac users: Ensure you have the precise JDK version prescribed here.

  2. Download the latest .jar file from here.

  3. Copy the file to the folder you want to use as the home folder for WatchDog.

  4. Open a terminal, cd to the folder containing the JAR file, and run java -jar addressbook.jar.
    A GUI similar to the one below should appear in a few seconds. Note how the app contains some sample data.

  5. Type a command in the command box and press Enter to execute it. For example, type help and press Enter to open the help window.
    Some example commands you can try:

    • list customer : Lists all customers.

    • list dog : Lists all dogs.

    • resetdisplay : Shows all customers and dogs, plus activities occurring today or later.

    • summary : Shows overall counts and today's activities and distinct enrolled dogs.

    • today : Shows today's activities, enrolled dogs, and their owners.

    • clear : Asks for Y/N confirmation before deleting all customers, dogs, activities, and enrolments. This action cannot be undone.

    • exit : Exits the app.

  6. Refer to the Features section below for details of each command.

Features

Notes about the command format:

  • Words in UPPER_CASE are the parameters to be supplied by the user.
    For example, in adddog n/NAME b/BREED s/SIZE, replace NAME with a value such as John Doe.

  • Items in square brackets are optional.
    For example, editdog ID [n/NAME] [b/BREED] [s/SIZE] allows you to specify only the fields to change.

  • Items followed by ... can appear zero or more times.
    For example, link c/7 d/42 d/51 links multiple dogs to one customer.

  • Parameters can be in any order.
    For example, if the command specifies n/NAME p/PHONE_NUMBER, p/PHONE_NUMBER n/NAME is also acceptable.

  • Extraneous parameters for some commands that take no parameters, such as help, exit, and clear, are ignored.
    For example, help 123 is interpreted as help. resetdisplay and summary reject extra parameters.

  • If you are using a PDF version of this document, be careful when copying and pasting commands that span multiple lines as space characters surrounding line-breaks may be omitted when copied over to the application.

The original AB3 person commands add, edit, delete INDEX and find are no longer supported. Use the customer and dog commands described below.

Viewing help: help

Shows a message explaining how to access the help page.

Format: help

Adding an activity: addactivity

Creates an activity schedule with zero dogs and reports its persistent ID. The schedule is saved across restarts. Activities with identical names or times are allowed and receive different IDs.

Format: addactivity n/NAME date/YYYY-MM-DD start/HH:mm end/HH:mm r/RECURRENCE

All five fields are required exactly once, in any order. Prefixes and recurrence values are lowercase. Use a nonblank name, a valid calendar date, and 24-hour times from 00:00 to 23:59. The end must be later than the start on the same day; overnight schedules are unsupported. Past start dates are permitted. Leading and trailing spaces in values are ignored. Space-separated alphabetic tokens ending in / are reserved for prefixes, including within names; unknown prefixes and extra text before the fields are rejected without creating an activity.

  • r/once: occurs only on the supplied date.
  • r/daily: occurs every day from that date, with no end date.
  • r/weekly: occurs on that date's weekday every week, with no end date.

Examples:

  • addactivity n/Grooming date/2026-10-20 start/14:00 end/15:00 r/once
  • addactivity n/Morning walk date/2026-10-20 start/09:00 end/09:30 r/daily
  • addactivity n/Training date/2026-10-20 start/10:00 end/11:00 r/weekly

Invalid dates, times, recurrence values, missing or repeated fields produce an error. Creation does not book any dogs, so overlapping empty schedules are allowed. Dog booking commands and activity cards are separate features; this contribution reports creation in the command feedback.

Deleting an activity: deleteactivity

Deletes the activity with the specified persistent ID. For a recurring activity, this deletes the entire series. All dogs enrolled in that activity are unenrolled; the dogs themselves and their enrolments in other activities remain. Deleted activity IDs are not reused.

Format: deleteactivity ACTIVITY_ID

Example: deleteactivity 21

The ID must be a nonnegative integer belonging to an existing activity. Invalid or missing IDs leave the activity and enrolments unchanged.

Editing an activity: editactivity

Edits an activity with the specified persistent ID. An activity can be edited only when it has no enrolments. If dogs are enrolled, the command leaves the activity unchanged and suggests creating a new activity instead.

Format: editactivity ACTIVITY_ID [n/NAME] [date/YYYY-MM-DD] [start/HH:mm] [end/HH:mm] [r/once|daily|weekly]

Searching activities: searcha

Searches activities by name, date, time, and/or recurrence. At least one field must be provided, and all supplied fields must match.

Format: searcha [n/NAME] [d/YYYY-MM-DD] [t/HH:mm] [r/RECURRENCE]

Example: searcha n/Dog run t/16:00

  • Name matching is case-insensitive (run and RUN are equivalent) and treats repeated internal spaces as one space.
  • Date matching includes activities that occur on the specified date, including daily and weekly recurrences.
  • Time matching is inclusive: an activity matches when the specified time is between its start and end times.
  • Recurrence matching accepts Once, Weekly, or Daily, and is case-insensitive.
  • Dates must use YYYY-MM-DD, and times must use 24-hour HH:mm format.
  • Only lowercase n/, d/, t/, and r/ field prefixes are accepted.
  • A successful command displays Successfully searched activities by followed by the supplied values, in the form name: NAME, time: HH:mm, date: YYYY-MM-DD, and recurrence: Once|Weekly|Daily. Unused fields are omitted. If there are no matches, the activity panel is empty.
  • The dog panel shows dogs enrolled in the matching activities; when a date is supplied, only enrolments on that occurrence date are included. The customer panel shows owners of those dogs.
  • Invalid date, time, or recurrence input displays Error in searching activities: followed by the applicable error message.
  • The filter remains active while activities are added or their state, enrolments, or details are changed.

Showing today's activities: today

Shows activities occurring today, the dogs enrolled in today's occurrences, and their owners.

Format: today

Example: today

  • The command is case-sensitive and accepts no additional fields.
  • Recurring activities are included when they occur today.
  • Dogs are shown only when they are enrolled in today's occurrence of an activity.
  • The command replaces the current activity, dog, and customer displays.
  • If there are no matching records, the relevant panels are empty.
  • Extra input produces Error in showing today: followed by Info is in the wrong format. Input in the correct format.

Adding a dog: adddog

Adds a dog and assigns it a unique persistent ID.

Format: adddog n/NAME b/BREED s/SIZE

Example:

  • adddog n/Cookie b/Chihuahua s/Small

Valid sizes are small, medium, large, and giant. Size input is case-insensitive. Dog names and breeds may contain letters, numbers, spaces, and must not be blank. Leading and trailing spaces in field values are ignored.

Adding a customer: addcustomer

Adds a customer and assigns it a unique persistent ID.

Format: addcustomer n/NAME p/PHONE_NUMBER e/EMAIL bc/BACKUP_CONTACT_NUMBER

Example:

  • addcustomer n/Lily Koh p/91234567 e/lily@gmail.com bc/98765432

The contact number and backup contact number must be eight-digit numbers.

Listing all customers: list customer

Shows a list of all customers in the address book.

Format: list customer

If there are no customers, WatchDog displays There are no customers to display.

Listing all dogs: list dog

Shows a list of all dogs in the address book.

Format: list dog

If there are no dogs, WatchDog displays There are no dogs to display.

Resetting the display: resetdisplay

Shows all stored customers and dogs, plus activities with an occurrence today or later according to the computer's local date. One-time activities before today are hidden. A daily or weekly activity remains visible while it has a future occurrence, even if its first date is in the past. Activity cards continue to show the schedule's first date. This command changes the view only; stored records are not changed.

Format: resetdisplay

Viewing daycare statistics: summary

Shows six statistics using all stored records, including records hidden by search or filters. The command preserves your records and filters.

Format: summary (no parameters; surrounding whitespace is accepted)

Example output:

Overall: 24 dogs | 18 customers
Activity schedules: 10 total | 7 from today onwards
Today (2026-10-24): 5 activities | 12 distinct dogs enrolled
  • Overall counts include dogs without owners and customers without dogs. Records with the same name but different IDs count separately.
  • Total activity schedules includes past one-time activities. Each recurring schedule counts once.
  • From today onwards counts schedules with an occurrence today or later, including recurring schedules that started earlier. It excludes past one-time activities.
  • Today's activities counts schedules occurring today, including activities with no enrolled dogs. All activity counts include empty activities and sessions that ended earlier today.
  • Today's distinct dogs enrolled counts each dog ID once across all activities on that date. Yesterday's and tomorrow's enrolments are excluded. Enrolment does not indicate attendance.

The date shown is read once when the command runs, using the computer's local date. Like other successful commands, summary is followed by the application's normal save attempt; a storage permission or save error can therefore appear instead of the statistics.

Editing a dog: editdog

Edits one or more details of an existing dog using its persistent ID.

Format: editdog DOG_ID [n/NAME] [b/BREED] [s/SIZE]

Example: editdog 1 s/Large

  • DOG_ID must identify an existing dog.
  • At least one dog field must be provided.
  • Any omitted field keeps its existing value.

Editing a customer: editcustomer

Edits one or more details of an existing customer using its persistent ID.

Format: editcustomer CUSTOMER_ID [n/NAME] [p/PHONE] [e/EMAIL] [bc/BACKUP_CONTACT]

Example: editcustomer 1 p/91234567 e/johndoe@example.com

  • CUSTOMER_ID must identify an existing customer.
  • Any supplied field replaces its existing value.

Linking dogs to a customer: link

Format: link c/CUSTOMER_ID d/DOG_ID [d/DOG_ID]...

Example: link c/1 d/2 d/3 links dogs 2 and 3 to customer 1.

  • Use persistent record IDs, including records hidden by a search. IDs range from 0 to 2147483647.
  • Put exactly one c/ field first, followed by one or more d/ fields, separated by whitespace. Prefixes are lowercase, and there must be no space between a prefix and its ID.
  • Each customer can own multiple dogs; each dog can have only one owner. Unlinked records are allowed.
  • Editing a dog's name, breed, or size preserves its owner. Use unlink to remove ownership.
  • Dog IDs must not repeat. Unknown fields, missing IDs, negative IDs and non-integer IDs are rejected.
  • If the customer or any dog does not exist, or any dog already has an owner (even the same customer), the entire command fails and no records change. Linking does not reassign dogs.
  • A successful command reports the linked IDs. Dog cards show Owner ID: CUSTOMER_ID, or Owner ID: None. Customer cards show Dog IDs: 2, 3 below backup contact, or Dog IDs: None if no dogs are linked. This field includes all owned dogs, even when search filters hide their cards. Existing search filters stay active; use list dog to see all dogs.
  • Links are saved automatically and survive restarting the application.
  • Deleting a customer unlinks their dogs without deleting them, including dogs hidden by a search. These dogs keep their IDs and details, show Owner ID: None, and can be linked to another customer. Other customers' dogs and unlinked dogs are unaffected. Deleting a dog does not delete its customer.

Unlinking dogs from a customer: unlink

Formats: unlink d/DOG_ID [d/DOG_ID]... or unlink c/CUSTOMER_ID

Examples:

  • unlink d/1 d/2 d/3 removes ownership from dogs 1, 2 and 3, even if they have different owners.

  • unlink c/1 removes ownership from every dog belonging to customer 1, including hidden dogs.

  • Use persistent IDs from 0 to 2147483647, lowercase prefixes, and whitespace between fields. Do not put whitespace after the slash. Repeated dog IDs (including d/2 d/02) are rejected.

  • Do not mix customer and dog prefixes. The customer form accepts exactly one customer ID.

  • For the dog form, every dog must exist and have an owner. If any dog is missing or unowned, the whole batch fails without changing anything.

  • For the customer form, the customer must exist and have at least one linked dog; otherwise an error is shown.

  • Unlinking never deletes customers or dogs, even when unlinking a customer's last dog. All other details stay unchanged. You can then use link to assign the dogs to another customer.

  • Dog cards show Owner ID: None; the customer's Dog IDs field removes the unlinked IDs, showing Dog IDs: None when none remain. Existing search filters stay active.

  • Changes are saved automatically and survive restarting the application.

Searching dogs: searchd

Searches dogs by one or more fields. All supplied fields must match.

Format: searchd [n/NAME] [b/BREED] [s/SIZE] [i/ID]

Example: searchd b/Golden Retriever s/Medium

  • Name and breed matching are case-insensitive substring searches.
  • Size must be small, medium, large, or giant, ignoring letter case.
  • ID matching is exact, and the ID must belong to a dog in the database.
  • A successful command displays Successfully searched dogs by followed by only the supplied fields.
  • Invalid input displays Error in searching dogs: followed by the applicable error message. Invalid or nonexistent dog IDs display Invalid dog id. Please input a valid dog id.
  • Invalid sizes display Invalid dog size. Please input small/medium/large/giant only.
  • The customer panel is also filtered to customers linked to the matching dogs.
  • The activity panel shows activities in which a matching dog is enrolled. For each displayed activity, an Enrolments section lists every matching dog as [DOG_ID]. [DOG_NAME]: DATE, DATE, .... Dates include past, present, and future enrolments and are sorted chronologically. The activity's normal date, time, and recurrence fields remain unchanged.
  • Unowned matching dogs remain visible, but the customer panel is empty.
  • The filter remains active while dogs or customers are added, edited, deleted, linked, or unlinked. Matching activities refresh when enrolments change.

Filtering unlinked records: filterun

Format: filterun dog or filterun customer

  • filterun dog displays dogs that are not linked to any customer and clears the customer panel.
  • filterun customer displays customers that do not own any dogs and clears the dog panel.
  • The category must be lowercase. Multiple spaces between filterun and the category are accepted.
  • The filter remains active while records are added, edited, deleted, linked, or unlinked.

Searching customers: searchc

Searches customers by one or more fields. All supplied fields must match.

Format: searchc [n/NAME] [p/PHONE] [e/EMAIL] [d/DOG_ID ...] [bc/BACKUP_CONTACT] [i/CUSTOMER_ID]

Example: searchc n/Anna d/12 34

  • Name matching is case-insensitive, uses a substring search, and treats repeated spaces as one space.
  • Phone and backup contact numbers require exactly eight digits and use exact matching.
  • Email matching is case-insensitive and exact.
  • Dog IDs must exist. A customer must own all specified dog IDs to match.
  • Customer ID must be a nonnegative ID belonging to an existing customer; it matches that customer exactly.
  • The dog panel is also filtered to show only dogs owned by the matching customers.
  • Dog IDs and customer ID appear in the success message only when supplied; dog IDs are displayed in ascending numeric order.
  • Only lowercase n/, p/, e/, d/, bc/, and i/ prefixes are accepted.
  • Invalid field values display Error in searching customers: followed by the applicable error message. Invalid or nonexistent dog and customer IDs have specific messages.
  • Unsupported field prefixes are rejected as invalid command formats.
  • If no customers match, the customer panel is empty.
  • The filter remains active while customers or their linked dogs are added, edited, deleted, linked, or unlinked. The activity panel shows only activities with enrolments belonging to the matching customers. Each activity includes an Enrolments section containing only their dogs and those dogs' stored enrolment dates.

Deleting a dog: delete dog

Deletes a dog using its persistent dog ID and removes all of that dog's activity enrolments, including past occurrences. Other dogs' enrolments and the activity schedules remain unchanged.

Format: delete dog ID

Examples:

  • delete dog 0
  • delete dog 0

Multiple spaces between the command components are accepted.

Upon success, WatchDog displays:

Successfully deleted dog <id>: <Name>; Breed: <breed>; Size: <Size>

If the ID does not exist, WatchDog displays:

Error in deleting dog:
Please enter a valid dog index

Deleting a customer: delete customer

Deletes a customer using its persistent customer ID.

Format: delete customer ID

Example:

  • delete customer 21

Customer and dog cards

The main list shows the currently selected category in a scrollable area. Customer cards show customer details. Dog cards show the persistent dog ID and name, followed by breed and size. Newly added records appear automatically. Customer and dog IDs belong to separate categories and may overlap. Dog and customer IDs belong to separate categories and may overlap.

Clearing all entries: clear

Clears all customers, dogs, activities, and enrolments from the address book after confirmation.

Format: clear

The app warns that this action cannot be undone and asks for confirmation (Y/N). Enter Y to clear all entries or N to cancel in the command box. Both answers are case-insensitive and accept surrounding whitespace. Any other input asks for Y/N again; enter N before running another command. No data or history changes until you confirm.

Examples:

  • Enter clear, then enter y to permanently delete all entries.
  • Enter clear, then enter n to cancel and keep all entries and undo/redo history.

Clearing also discards the undo and redo history, so clear cannot be undone. This remains true if the command changes memory but its save fails.

Undoing and redoing a command: undo, redo

undo restores the stored records and displayed view from before the most recent undoable command. redo restores the records and view from just before that undo. Both commands attempt to save the restored records automatically.

Formats: undo or redo

For example, after adddog n/Cookie b/Chihuahua s/Small, enter undo to remove Cookie, then redo to bring Cookie back. You can undo the redone command again.

Only one command can be undone at a time. A later successful undoable command replaces that history and makes redo unavailable. View-changing commands such as search, filter, selection, and resetdisplay are undoable too. help, summary, and exit preserve both undo and redo history; parse errors and commands rejected before execution also leave history unchanged. The history is cleared after confirming clear with Y and is not retained when WatchDog restarts. Surrounding whitespace is accepted, but neither command accepts arguments. If no command is available, WatchDog displays There is no command to undo. or There is no command to redo.

A save error can occur after an undoable command, undo, redo, or clear has changed memory. The change remains visible in the current session, with the corresponding undo or redo operation available where applicable, but the data file may not contain that change.

Exiting the program: exit

Exits the program.

Format: exit

Saving the data

WatchDog automatically saves data after every command. You do not need to save manually.

Editing the data file

WatchDog data is saved automatically as a JSON file [JAR file location]/data/addressbook.json. Advanced users are welcome to update data directly by editing that data file.

Caution: If your changes make the data file invalid, WatchDog starts with an empty address book at the next run. The invalid file remains on disk until you run a command (WatchDog saves after every command). Still, we recommend backing up the file before editing it.
Furthermore, certain edits can cause WatchDog to behave in unexpected ways (e.g., if a value entered is outside of the acceptable range). Therefore, edit the data file only if you are confident that you can update it correctly.

FAQ

Q: How do I transfer my data to another computer?
A: Install the app on the other computer and overwrite the data file it creates with the data file from your previous WatchDog home folder.

Known issues

  1. When using multiple screens, if you move the application to a secondary screen, and later switch to using only the primary screen, the GUI will open off-screen. The remedy is to delete the preferences.json file created by the application before running the application again.
  2. If you minimize the Help Window and then run the help command (or use the Help menu, or the keyboard shortcut F1) again, the original Help Window will remain minimized, and no new Help Window will appear. The remedy is to manually restore the minimized Help Window.
