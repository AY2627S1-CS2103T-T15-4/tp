Design

Persistent identities

Customers, dogs and activities use persistent IDs as their identities. These IDs are assigned by the address book and are stored with the records, so they remain stable across application restarts and are not affected by filtering, list positions or deletion of other records. This allows commands and relationships to refer to a record reliably even when the visible list changes.

Customer–dog ownership

LinkCommandParser accepts one customer ID followed by one or more distinct dog IDs. LinkCommand delegates the batch to Model.linkDogs; ModelManager forwards to AddressBook. The address book looks up persistent IDs in the complete lists and validates every endpoint and ownership constraint before publishing one replacement dog list. A rejected batch throws LinkException without changing records or filters; the command translates it to CommandException for user feedback.

Each immutable Dog stores an optional owner customer ID. This is the single source of truth; customers do not store a duplicate dog-ID list. A dog may be unlinked or have one owner, while a customer may own any number of dogs. Linking an already-owned dog is rejected, including links to the same owner. Dog equality includes ownership, while identity remains the persistent dog ID.

UnlinkCommandParser accepts either one customer ID or one or more distinct dog IDs; mixed prefixes are rejected. UnlinkCommand delegates to Model.unlinkCustomerDogs or Model.unlinkDogs and translates UnlinkException into command feedback. AddressBook validates every selected dog exists and has an owner before publishing one replacement list of unowned copies. Dogs may belong to different customers. The customer form validates the customer, selects all their dogs from the complete list, and uses the same atomic batch operation. Missing customers and customers with no linked dogs are rejected. Unlinking preserves records and filters, including a customer's last dog, and uses the existing nullable ownerId storage field without a schema change.

AddressBook.removeCustomer clears ownership of that customer's dogs, regardless of filters, preserving their persistent IDs and details. Unowned dog cards show Owner ID: None. Removing a dog leaves its customer intact. Customer edits must preserve persistent IDs to keep links valid. Observable list updates refresh dog cards, which display owner IDs without changing search filters. Customer cards display owned dog IDs below backup contact. RecordListPanel observes the complete dog list as well as visible records, so these IDs remain accurate when dog cards are filtered out.

JsonAdaptedDog persists ownerId. A missing or null field means unlinked, preserving compatibility with older files. Negative owner IDs and references to missing customers are rejected on load; customers are restored before dogs. Copies of the address book retain ownership through immutable dogs. EditDogCommand preserves the current owner ID when constructing a replacement dog, so editing details does not unlink the dog. Ownership changes remain explicit through linking, unlinking, or customer deletion.

Dog–activity enrolment

Dog participation in an activity is represented by a separate Enrolment record containing an activity ID and a dog ID. This separates the reusable activity schedule from the dogs attending it. It also allows dogs to be enrolled or unenrolled independently without modifying the activity's schedule or storing duplicate dog objects inside Activity.

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete dog 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, RecordListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

RecordListPanel observes the filtered customer and dog lists, plus the complete dog list exposed by Logic. It displays customers followed by dogs in a single list, using CustomerCard and DogCard. List changes rebuild the card factories; JavaFX creates card nodes as cells need them. Cards use persistent IDs, not row numbers. The complete dog list supplies ownership details independently of filters.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Customer and Dog objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteDogCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteDogCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a dog).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

Model component

API : Model.java

The Model component,

  • stores customers and dogs in UniqueCustomerList and UniqueDogList, with persistent IDs and dog ownership links.
  • exposes separate unmodifiable observable customer and dog lists for search and category filtering. The UI observes these lists to update cards when records or filters change.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Removal of the legacy person feature

WatchDog uses customer and dog records. The original AB3 person records, tags, person-only commands (add, edit, delete INDEX and find), person storage adapters and unused list panels have been removed. Shared components such as AddressBook, preferences, parsing utilities, help, clear and JSON storage remain in use.

Existing JSON files may contain a legacy persons field. It is ignored on loading and omitted on the next save; its records are not converted to customers. Customer/dog records, ownership links and both next-ID counters are preserved. A file containing only legacy persons loads as an empty WatchDog book. No startup sample person records are created.

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

Adding dogs

AddDogCommandParser validates the dog details supplied by the user and creates an AddDogCommand. The command delegates to Model, which forwards the request through ModelManager to AddressBook.

The address book assigns the dog a persistent ID when it is added. The ID is allocated from a monotonically increasing counter rather than from the dog's position in the list, so deleting a dog does not change the identities of the remaining dogs. The counter and dog IDs are persisted so that new dogs continue to receive unique IDs after the application restarts.

The following diagram shows the add-dog command flow. The important part of this flow is that the persistent dog ID is assigned by the address book only after the command reaches the model layer.

Editing dogs

EditDogCommandParser parses the persistent dog ID and the fields to be edited. The command uses the ID to locate the dog in the complete dog list rather than relying on a filtered-list position. AddressBook validates the replacement details and publishes the updated dog while preserving its persistent ID and current owner relationship.

The following diagram shows the edit-dog command flow. The command locates the dog using its persistent ID, so editing remains independent of the current filtered-list position. The replacement dog retains both its ID and owner relationship.

Selecting a dog

AddressBookParser routes select to SelectDogCommandParser. The parser accepts only the lowercase category dog and a nonnegative integer ID. SelectDogCommand looks up that ID in the complete dog list. A missing dog leaves every filter unchanged.

On success the command asks ModelManager to follow that dog id. The three filters read the current records whenever dogs, customers, activities, links, or enrolments change, so the columns stay current after later commands. The dog list shows the selected dog. The customer list shows that dog's current owner, or nothing when the dog is unlinked. The activity list shows current enrolments that are not marked completed and whose schedule still occurs today or later, using Activity.nextOccurrenceOnOrAfter. A marked activity is hidden, and unmarking it shows it again. Another command that sets its own filter, such as list or search, leaves this view. ModelManager keeps this filtered activity list separately from getActivityList(), which continues to expose every stored schedule.

Activity creation and storage

The following partial class diagram shows the activity schedules and their integration with the model. An activity represents a reusable schedule; its occurrence dates are calculated from its recurrence rule.

AddressBookParser routes addactivity to AddActivityCommandParser. The parser requires n/, date/, start/, end/, and r/ exactly once, rejects unknown alphabetic prefixes, and validates strict calendar dates, minute-resolution 24-hour times and lowercase recurrence. The immutable command validates a details snapshot with an unused ID of zero. Parsing never allocates an ID. execute calls Model.addActivity(ActivityName, LocalDate, LocalTime, LocalTime, Recurrence) and reports the identified schedule returned by the model. No dog/customer filters change.

ModelManager delegates to AddressBook.addActivity. The address book validates the complete schedule before assigning the next ID and publishing it through getActivityList(), an unmodifiable observable view of all schedules. Creation allows identical details and overlapping empty schedules. The first allocated ID is one; the monotonically increasing counter is stored as a long so that Integer.MAX_VALUE + 1 can represent exhaustion without wrapping. ID exhaustion rejects creation. Copy/reset and equality include activities and the counter. Existing customer/dog APIs are unchanged.

JsonAdaptedActivity stores the six schedule fields; dates/times use ISO strings and recurrence uses its enum name. JsonSerializableAddressBook stores activities and nextActivityId, validates identities and the counter, and rejects invalid schedules or null entries. Older files with no activity fields load an empty collection. A missing counter is derived from the largest stored ID; an explicit counter must exceed every stored ID and cannot exceed the exhaustion sentinel. Activity IDs and the counter must be integer JSON numbers; fractions, numeric strings and out-of-range numbers are rejected before conversion. Reset updates the activity counter before notifying activity-list listeners, so listeners can copy the model with a consistent identity state. LogicManager uses its existing save path after successful command execution.

The following sequence diagram shows successful execution of addactivity n/Training date/2026-10-20 start/10:00 end/11:00 r/weekly. The command uses the Model interface, implemented by ModelManager; saving uses the Storage interface, implemented by StorageManager. Concrete lifelines are shown to make the delegation clear.

Activity filtering

AddressBookParser routes filtera to FilterActivityCommandParser. The parser accepts at least one of the lowercase fields n/, d/, t/, and r/, rejects duplicate or unknown fields, and validates dates and times using strict YYYY-MM-DD and HH:mm formats. Recurrence is restricted to Once, Weekly, or Daily. Names are trimmed, internal whitespace is normalised, and matching is case-insensitive.

FilterActivityCommand applies an ActivityFilterPredicate to the model's filtered activity list. Name matching uses a case-insensitive substring, date matching delegates to Activity.occursOn(date) so recurring activities are handled correctly, and time matching includes both endpoints. Multiple recurrence matching compares the activity's stored recurrence. Multiple fields are combined with AND semantics. The activity panel observes this filtered list, while the underlying stored schedules remain unchanged. The success message reports only the supplied fields, in the order name, time, date, and recurrence.

Activity enrolment and completion

Dogs are linked to activities through separate Enrolment records. Each record stores an activity ID and a dog ID, allowing an activity to have multiple dogs without storing dog objects directly inside the reusable activity schedule.

Users can enrol or unenrol one or more dogs using:

enrol a/ACTIVITY_ID d/DOG_ID1,DOG_ID2
unenrol a/ACTIVITY_ID d/DOG_ID1,DOG_ID2

The parser converts the activity ID and comma-separated dog IDs into a command. The command delegates through Model and ModelManager to AddressBook, which verifies that the activity and dogs exist and that the requested enrolments are valid before updating the enrolment list. Enrolment changes are persisted with the address book.

Unenrolment follows the same parser and model delegation path. After validation, the address book removes the matching existing enrolment records instead of changing the activity schedule itself.

Activities can be marked as completed or restored to an incomplete state using:

mark ACTIVITY_ID
unmark ACTIVITY_ID

Activity remains immutable. Marking or unmarking creates a replacement activity with the same identity and schedule but a different completion status. The updated status is included when the address book is saved.

Unmarking follows the same flow as marking, but replaces the activity with a copy whose completion status is false.

The sequence diagrams focus on interactions between application layers. Low-level list operations and exception propagation are omitted where they do not affect the overall design.

Design considerations

Use Model.getActivityList() for observing activities and Activity.getId() for identity, independently of displayed positions. Use Activity.occursOn(date) for dated schedule queries. Enrolments are stored separately from activity schedules and are keyed by activity ID and dog ID. The activity card UI is outside this contribution. addActivityFromStorage and setNextActivityId are restoration APIs, not command entry points.

AddActivityCommandParserTest, AddActivityCommandTest, ActivityIntegrationTest and ActivityStorageTest cover parser failures, unchanged state, observable access, identity boundaries, all recurrence modes, old files and command-to-disk round trips using temporary files.

Dog and customer search

Without a category, SearchCommandParser accepts one name or ID field and creates a SearchCommand. It reuses CustomerSearchPredicate and DogSearchPredicate to update both observable lists. Customer and dog IDs are independent, so an ID search can match both categories. The existing RecordListPanel renders customers first, then dogs; feedback reports both counts.

AddressBookParser routes search to SearchCommandParser, which dispatches explicit categories. The three search parsers delegate shared name/ID validation to SearchFieldParser while retaining their own category grammar, command creation and usage messages. For dog searches, SearchDogCommandParser accepts dog n/NAME_QUERY or dog id/ID. It rejects empty values, additional prefixes, unsupported categories and invalid IDs before command execution. IDs are nonnegative Java integers; they are not AB3's one-based list indices.

DogSearchPredicate delegates name matching to StringUtil.containsSubstringIgnoreCase and compares IDs directly with Dog.getId(). A name query is one literal substring, including internal spaces. SearchDogCommand updates the model's filtered dog list and hides customer cards using the customer filter. Logic.getFilteredDogList() supplies the observable list to RecordListPanel, so matching dogs appear as cards. CommandResult contains only the match count. Each new predicate applies to all stored dogs, without changing stored records. list dog resets the dog filter so all dogs can be displayed again after a search.

SearchDogCommandParserTest covers command routing, whitespace, prefix misuse and ID boundaries. DogSearchPredicateTest covers field selection and matching. SearchDogCommandTest exercises the real model, including duplicate names, consecutive searches and unchanged stored records. RecordListPanelTest checks that search and list commands update the displayed cards.

Customer search follows the same command/parser/predicate structure through SearchCustomerCommandParser, SearchCustomerCommand and CustomerSearchPredicate. SearchCommandParser dispatches the customer category to its parser and retains dog parsing. The command updates the existing customer filter and hides dogs using the dog filter. Customer names use StringUtil.containsSubstringIgnoreCase; IDs use Customer.getId(). Search does not depend on an add-customer command: any customers loaded into the model can be searched. Tests populate the model directly and verify filtering, persistent IDs, unchanged records and card updates.

Appendix: Requirements

Product scope

Target user profile:

  • Is a dog day care centre manager
  • Has a need to manage multiple dogs and customers
  • Has a need to keep track of each dog’s information and schedule
  • Has a need to keep track of every dog’s owner and their information
  • Can type fast
  • Prefers typing to mouse interactions
  • Is reasonably comfortable using CLI apps

Value proposition: WatchDog helps dog day care centre managers to manage and keep track of all their clients’ dogs, each of the dog’s needs and client information in a centralised application, faster than with a typical mouse-driven GUI application.

Non-Functional Requirements

NFR-01. Platform compatibility: Should work on any mainstream OS as long as it has Java 25 or above installed.

NFR-02. Offline operation: After installation and setup, all core dog and customer management operations shall work without an internet connection.

NFR-03. Performance: With up to 500 dog records and 500 customer records, WatchDog shall display the result of an add, edit, delete, list or search command within 2 seconds of submission on the agreed test laptop.

NFR-04. Startup time: With the same dataset, WatchDog shall load its saved records and become ready to accept commands within 10 seconds of launch on the agreed test laptop.

NFR-05. Keyboard usability: After launch, users shall be able to perform all core dog and customer management operations using the keyboard without requiring mouse interaction.

NFR-06. Typing efficiency: A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.

NFR-07. Error clarity: For invalid command syntax, missing required fields or invalid field values, WatchDog shall display an English error message identifying the problem and providing the expected format or accepted values.

NFR-08. Robustness: An invalid command or an input that fails validation shall not terminate the application or change existing records. The application shall remain ready to accept the next command.

NFR-09. Data persistence: Following successful data changes and a normal application exit, WatchDog shall restore the updated dog records, customer records and their associations when reopened.

NFR-10. Privacy: WatchDog shall store dog and customer records locally and shall not transmit their contents to external services.

Glossary

  • WatchDog: The application used to manage a dog daycare centre's customer and dog information.
  • User: The person operating WatchDog, primarily the dog daycare manager.
  • Customer: A person whose contact details are recorded because they use the daycare's services for their dog or dogs.
  • Dog record: The information stored about an individual dog, including its ID, name, breed and size.
  • Customer record: The information stored about a customer, including their ID, name, primary contact number, email and backup contact number.
  • Dog ID: A unique integer assigned by WatchDog to identify a dog record. Dogs with the same name are distinguished by their IDs.
  • Customer ID: A unique integer assigned by WatchDog to identify a customer record. Customers with the same name are distinguished by their IDs.
  • List index: A record's position in the currently displayed list. Unlike a record ID, this position may change when the list is filtered or reordered.
  • Dog-customer association: The recorded relationship indicating which customer owns a dog.
  • Primary contact number: The customer's main telephone number, used as the first contact option.
  • Backup contact number: An alternative telephone number used when the customer cannot be reached through their primary number.
  • Breed: The recorded breed or breed mix of a dog, such as Chihuahua, Shiba Inu or a mixed breed.
  • Dog size: The dog's recorded size category: small, medium, large or giant, according to the size chart adopted by the team.
  • Scheduled attendance: A planned visit by a dog to the daycare. A scheduled dog is not necessarily currently present.
  • Check-in / Check-out: Recording a dog's arrival at or departure from the daycare.
  • Present dog: A dog that has checked in and has not yet checked out.
  • Activity: A care task planned for a dog, such as feeding, grooming or exercise.
  • Checklist: A list of a dog's activities with an indication of which have been completed.
  • Aggressiveness: Recorded tendency to show threatening or potentially harmful behaviour towards humans or other dogs, including any known triggers.
  • Temperament: A dog's usual behavioural tendencies, such as being calm, shy or friendly. This is broader than aggressiveness.
  • Care instructions: Recorded directions for looking after a particular dog, including feeding, exercise and special precautions.
